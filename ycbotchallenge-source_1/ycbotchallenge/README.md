# YCBotChallenge (Fabric client mod, MC 1.21.11)

You play on your own client, press **G**, and the bot runs: walk to the nearest mob, tap it once (the server's auto-attack does the rest), wait for the kill, move to the next. Press **G** again to stop. A HUD shows live pacing; everything is logged to JSONL for the analyze/sim tools.

Built and compiled against Minecraft 1.21.11 / yarn 1.21.11+build.6 / Fabric API 0.141.6.

## Install

Drop `ycbotchallenge-0.9.12.jar` into your `mods/` folder alongside Fabric Loader (>= 0.16) and Fabric API for 1.21.11. Client-side only — nothing needed on the server.

## Use

- **G** toggles the bot (rebind in Controls → Misc). **Shift+G** toggles sprinting on/off (saved to the config; shown on the HUD).
- HUD (top-left) shows on/off, current action, live sidebar bals (money/souls/essence/shards/credits), TTK + zone readiness %, kills + kills/min, and the upgrade line: `bal`, `+/min` income, `need` remaining and `~ETA` to the next tier.
- Logs land in `.minecraft/ycbotchallenge-logs/events-<label>-<timestamp>.jsonl` — same schema as the mineflayer bot, so `analyze.js` and `simulate.js` from the bot project work on them unchanged (note: the toggle events are now named `bot_on` / `bot_off`).

## Config

`config/ycbotchallenge.json` (created with defaults on first run):

- `reach`, `targetRange` — tap distance and how far it will walk for a mob.
- `tapCooldownMs`, `reactionDelayMinMs/MaxMs`, `idleChancePerMinute` — humanization.
- `approachClickCpsMin/Max` (2–3), `approachClickMaxDist` (6) — anticipatory swing spam while closing in, with a vigor multiplier re-rolled every few seconds so the tempo wanders. Mostly whiffs at air, like a real player running up. Set max 0 to disable.
- `movement: false` — stand still and only tag what wanders into reach.
- `zoneMin`/`zoneMax` — `[x, y, z]` arrays bounding the farming zone (null = anywhere).
- `runLabel` — tag for the log file (`"baseline"`, `"asc6-geared"`, `"2x-souls"`, ...). Change it between experiment runs.
- `rebirthsPattern`, `sidebarCurrencies`, `ascensionChatPatterns`, etc. — the sidebar/chat parse knobs, in case your display format changes.

### Economy (upgrade loop)

Chat-driven, zero-spam, buy-or-wait. `/swordmax`, `/zone max` and `/rebirth` are **never polled** — every send is event-driven with a plausible human reason, and each goes through the humanized typing pipeline (kill-lull gating, log-normal pauses, typos).

**The balance is the sidebar.** The `5.62T ᴍᴏɴᴇʏ` row is reread every second and is the only money figure the bot uses. Money is credited per kill about a second after the boss bar vanishes (logs: kill 20:56:44.6 → row 20:56:45.5). `Reward Summary: (60s)` → ` + 17.19B Money` feeds only the income *rate* (HUD ETA). The 0.9.x money book (`/bal` seed, accrual, projection) is gone — it invented money between anchors and wrote its estimate back over the live row.

**Fail lines are gaps, not prices.** `You need 781.04B Money to purchase the next sword upgrade` is how far short you are — it shrinks as you earn (logs: 781.04B → 732.08B → 683.12B). The absolute next-tier price is `sidebar balance at fail + gap`, self-correcting on every fail. If the balance is somehow unknown at fail time the gap itself becomes the retry floor, so a kind can never latch shut.

**Evaluation triggers.** An evaluation is armed by a kill, by a sidebar money **increase** (`evalOnMoneyIncrease` — the kill credit itself, which also covers kills the client missed), and by a timer (`evalFallbackMs`, 30s) as the backstop. 0.9.6 was kill-only and sat on 8B→21B with a 1.24B sword for 108s because nothing died. Each eval waits for the board to settle (`postKillEvalDelayMin/MaxMs`, `upgradeSpendSettleMs`).

**The buy loop.** If the balance covers a known price, the bot waits a humanized notice delay (`buyNoticeDelayMin/MaxMs`, 2–8s) and types the command. A fail line updates the price and it goes quiet. Success is read from the server's own line when there is one — `You have unlocked a new sword level for 1.24B!` (one per level; `/swordmax` buys every level it can, so the **last** amount is the retry floor for the next tier) and `You have purchased new stage(s)!` — else **silence within `successSilenceMs` (3s)** counts as success. After a success the price resets to unknown and the next attempt waits until the balance passes the old price again (`retryPriceGrowthPct` margin). Unknown prices get one exploratory send per kind: **zone first while the TTK gate is open** (0.9.16), sword first while it is closed. `upgradeMinIntervalMs` (60s) per kind is a backstop ceiling, collapsed to `commandCooldownMs` while the balance is `cooldownRelaxBalanceMult` (3×) over the kind's last price (right after a rebirth the balance grows 10× a minute; logs show zone skipped for "cooldown" from 8M to 220M).

**Strict chat gate.** Upgrade lines classify only within `upgradeResponseWindowMs` (4s) of our own send, never on player/broadcast lines (`»` or `[rank]` prefix), and only via anchored patterns. This kills the 0.8.x failure mode where `EnchantedMC »` broadcasts matched the loose `enchanted` success pattern. Unrecognized lines are raw-logged (`upgrade_response_raw`) for 6s after each send, so reply formats are always captured for evidence-based tuning.

**Zone.** Same model for `/zone max` (fail gap → `zoneTarget = bal + gap`), behind the hard TTK gate below. A successful zone advance teleports you, so the stop protocol exempts displacements for `expectedTeleportAfterZoneMs` (8s) after our own zone send. EnchantedMC's sidebar has **no Zone row**, so zone changes come from our own teleport (`zone_teleport`), the mob level prefix on boss bars (`LVL2 Rabbit` → `LVL5 Goat`, logged as `boss_level`, debounced over two polls), the `All mobs have been respawned in your zone.` broadcast, or a `Zone N` row where a server has one. Any of them fires `zone_change`, clears the TTK window and forces a full targeting reset (`zone_retarget`).

**Rebirth reset.** A rebirth zeroes money and resets sword/zone progression, so every learned price is stale the moment it happens. Detected two ways: the sidebar `rebirth: N` counter incrementing (or resetting, for ascensions), and a money collapse (≥1B → ~0 while we didn't just buy something). Either wipes all learned prices, gaps, maxed flags, and seed flags (`economy_reset` event) — the loop re-discovers post-rebirth prices with one fresh seed send per kind.

**Sword vs zone: a TTK gate with rolled patience.** `/zone max` is refused — affordable or not — while the *effective TTK* is above this stage's **patience** or unknown. Since 0.9.23 the effective TTK is the rolling kill median (`ttkWindowKills`) as soon as three kills of the stage have landed — what actually happened — and the DPS-predicted whole-mob time (`HP at tag / boss-bar DPS`) only before that, and only while it is fresh (`predictedTtkMaxAgeMs`, 4s: a prediction describes the mob it was read from and is refreshed every tick while that mob is cooked; instant kills never produce one). Patience is not a fixed 10s line: every zone change and enable rolls it log-normally between `zoneMaxTtkMs × zonePatienceMinMult` (0.6) and `× zonePatienceMaxMult` (1.6), logged as `zone_patience`, so the same 8s median opens the gate one stage and closes it the next; `upgrade_plan`/`upgrade_skip` carry `ttkVia` (median/predicted) and `patienceMs`. The window is cleared on every zone change, so the previous stage's fast kills can never open the gate for the next stage. This is what stops the 0.9.5 spiral, where a readiness value pinned at 100% bought three zones against three swords and TTK went 0.25s → 3.8s → 7.2s → 75s → 90s until nothing died. With the gate open the **zone is the buy** (0.9.16): bought when affordable, probed first when its price is unknown, saved for otherwise. Rebirth, once its gap is known and covered, pre-empts both.

**Zone first, then sword, then rebirth (0.9.16).** The 03-36 post-rebirth log settles the order: every zone step multiplied per-kill money ×20 (58.7K → 1.17M → 23M → 462M → 9.2B → 183B) and cost about one kill of the next zone (137B for zone 6 whose kills pay 183B), so it pays back on the first kill even at a 42s TTK; a sword tier costs ×3.5 the last and halves the TTK only until the TTK reaches the movement floor (0.7–2s), after which it does nothing (zone 1: 675K spent on swords at 0.73s next to a 145K zone; zone 3: 376M before a ~250M zone). The priority is therefore: rebirth when covered; **sword while the gate is closed** (TTK above `zoneMaxTtkMs`, the only thing that helps and the guard against the zone spiral); **zone while it is open** — and while saving for a known zone price a sword is bought only when it costs at most `swordWhileSavingMaxPct` (25%) of the remaining gap and the TTK is above `zoneInstantTtkMs` (2s). Held swords log `upgrade_skip reason=saving-zone` (`zoneGap`, `swordPct`, `ttkMs`); `upgrade_plan` carries `priority`; the HUD shows `(sword waits for zone)`. `zoneOverSwordRatio` is legacy and inert. HUD prints the live `need` and `~ETA` to the next tier from the summary rate, and a `cd 41s` remainder when a cap is holding; `status` events carry `zoneReady` (1.0 with the gate open, `zoneMaxTtkMs / ttk` above it).

**Rebirth horizon (0.9.15).** A sword or zone bought before a rebirth is lost with it, so it has to pay for itself first. With income I per minute, price P, remaining gap G to the rebirth and an income multiplier g expected from the buy, staying rebirths in G/I minutes and buying in (G+P)/(I·g); the bot buys only when that is sooner, i.e. **P < G·(g−1)** (`rebirthHorizonZoneGain` 1.3, `rebirthHorizonSwordGain` 1.25, `rebirthHorizonEnabled`). Evidence from 2026-09-03: with the 900T rebirth 475T away at 109T/min (4.4 min), the bot bought zone 8 for 415T; income rose to ~148T/min but the rebirth was still 314T away 8 min later. In an earlier session zone 7 for 7.55T against a 22T gap turned a 9-min rebirth into a 14-min one. Early-snowball buys (K–B prices against a T gap) pass untouched. Blocked buys log `upgrade_skip reason=rebirth-horizon` with `rebirthEtaMin`, `buyEtaMin`, `gain`, `gapPct`; the HUD shows `eta 4m` next to the rebirth target and `(saving; zone waits)`. Every sword/zone success is followed `rebirthHorizonGainWindowMs` (3 min) later by an `upgrade_gain` line (income before/after, ratio, kills) so the gain knobs can be tuned from evidence; it is not used for decisions.

**Cook timeout.** `maxCookMs` (90s) abandons a tagged mob only once its boss-bar HP has also stopped dropping for `cookStallMs` (15s). Fresh-stage mobs can legitimately take that long (the Goat in the logs died at 89.8s; 0.9.6 abandoned the next one at 90.0s, one second before it died, and lost the kill credit and its 6.48B).

**0.9.25: the suffix ladder heals itself.** QQ was the third suffix this server taught us the hard way (Q in 0.9.6, Qa guessed wrong in 0.9.19, QQ in 0.9.24), and the rebirth cost grows ~30× per rebirth, so a new one arrives every second or third rebirth. The money row is read every second, and the one moment a new suffix's scale is provable is the rung crossing: `903.74T` one poll, `1.1Q` the next. So the built-in table is now only what the server has printed (K M B T Q QQ), and every change of the money row's suffix is judged by one rule (`Amounts.crossing`): the new suffix is the next 1000× rung iff its mantissa is in [1, 1000), the previous poll is at most 5 s old, and `mantissa × scale(previous) × 1000 / previous value` lies in [0.95, `suffixCrossingMaxJump` (20)] — adjacent rungs differ by 1000× while the band spans ~20×, so a spend, a rebirth collapse or a two-rung skip lands out of band. Every rung change logs `suffix_crossing` (from, to, verdict, reason, ratio), on the known rungs too, so the rule proves itself on the live board once per rebirth cycle. A fit on a suffix the table lacks is `suffix_learned` (confirmed when its basis was) and persisted with provenance in `config/ycbotchallenge-suffixes.json` (delete it to relearn). A suffix a chat line names before the board showed it (`$20.5QQQ` at a 2.66Q balance) or a board that is already on an unseen rung at enable gets the rung above the highest known scale, marked provisional (`suffix_guess`, `upgrade_chat provisional=true`, `balance provisional=true`); the balance must climb through that rung before it can afford anything quoted in it, and that crossing is `suffix_confirmed` or `suffix_corrected` — a correction forgets every provisional rung built on the wrong one and drops learned prices expressed on it (`dropped`, relearned from the next fail line). Config `suffixScales` win over learned scales and are never touched; `suffixLearningEnabled` false restores the 0.9.24 behavior. Above the top known rung, values print as a growing mantissa (`2500QQ`) rather than a guessed label.

**0.9.29: nothing typed before the first kill.** `upgrade_plan kind=sword` fired 5 s after each enable with zero kills (00:19 log; the kill counter carries over a toggle, so the first eval read as a kill) and `via=timer` 32 s into a session before any kill (17:57). Now no `/swordmax` or `/zone max` goes out before a rolled `upgradeFirstKillsMin..Max` (1–3) kills since the enable *and* since the last rebirth (`upgrade_skip reason=first-kills`); the phantom first eval is gone.

**0.9.24: QQ, and a /rebirth probe that never loops.** The 18:37 log: the stale-floor probe opened `/rebirth`, clicked the diamond, and the server answered `You need $20.xQQ Money to Rebirth.` — a suffix the parser did not know (`latest.log`: `Unknown amount suffix 'QQ'`), so the line was held as the first half of a split fail, nothing was recorded, the 2s settle timed out, and the abort path re-typed `/rebirth` 8–20s later — five times in 80s — until a closed GUI was read as a rebirth (`upgrade_result kind=rebirth via=silence`, `economy_reset via=upgrade-success` with the balance still 2.66Q). Now: `QQ` = 1e18 is built in; a need line with a suffix the parser still cannot scale logs `amount_unknown` (kind, token, suffix, raw) and resolves the send as a fail (`upgrade_result via=unknown-amount`) instead of a timeout; a rebirth is confirmed only by the server's own signals — its chat line, the sidebar counter, the money collapse — inside `rebirthSignalWaitMs` (6s) after the click, never by a GUI that merely closed (`upgrade_abort reason=no-signal`, no economy reset); and an aborted probe is re-typed only when it never reached the GUI (`no-gui`/`no-diamond`), at most `rebirthProbeMaxRetries` (1) per session (`rebirth_probe_retry` / `rebirth_probe_unresolved`).

**0.9.23: the gate reads real kills, patience is a mood, stale floors get probed.** The 17:57 log (rebirth 4 → 5 mid-session) showed the sword bias after a rebirth: the first chicken on zone 1 took 11.5s with the level-0 sword, its DPS prediction went into `lastPredictedTtkMs`, and because the prediction outranked the median it sat in every eval for the next two minutes (`"ttkMs":11502,"zoneGate":"closed"` × 34) while `zone_benchmark` medians fell 1206 → 301 ms — one-click chickens never refresh a prediction. Result: 2.57M + 6.43M + 22.52M of swords, zero zone probes, on a stage where the zone is the buy (the 17:31 run, enabled fresh on zone 1 with no stale prediction, bought five zones in four minutes). Three changes, one idea — decide from what is actually happening, with a human's tolerance rather than a line: (1) median first, prediction only before three kills and only while fresh; (2) patience rolled per stage (`zone_patience`); (3) the persisted rebirth floor is a lower bound from an earlier rebirth — once the balance sits on it with no rebirth having fired it is stale (155Q against a 900T floor from rebirth 3; the ~800Q cost of rebirth 5 was never learned, the horizon rule had no target, and a 489Q sword went out two minutes before the auto-rebirth), so the one-per-session `/rebirth` seed probe is due (`upgrade_plan kind=rebirth via=stale-floor`) and the horizon rule gets its target. No phase machine for early-vs-late in the rebirth cycle: kill speed (patience) covers the early snowball and the horizon rule covers the approach, both continuous; what had broken was their inputs.

The sidebar is reread every second: the money row feeds the buy path directly, other currencies (`sidebarCurrencies`) are logged, and snapshots publish every `scoreboardSnapshotMs` (5s). `debugSidebar` defaults to **true** while parsers are tuned from live evidence — every new sidebar row lands in the JSONL as `sidebar_raw`. Money values in the JSONL are suffixed strings (`75.1B`), not scientific notation. The suffix order is the server's, K M B T **Q QQ** … (`1.25Q` = 1e15 in the fail lines; the server's quintillion is written `QQ`, seen 2026-09-03 18:43 as `You need $20.xQQ Money to Rebirth.` after a 2.66Q balance — 0.9.24). Nothing above QQ is built in: the ladder heals itself (0.9.25, below). The first sighting of each suffix on the sidebar logs `amount_suffix` with the row before it and its `confidence` (builtin/learned/provisional/config); a 99% money drop that does not land below `moneyCollapseMaxValue` (1T) is logged `suffix_scale_suspect` instead of being taken for a rebirth, and a provisional suffix never triggers the money-collapse reset. Manual overrides go under `suffixScales`. Config knobs auto-migrate (`configVersion` 11 forces the 0.9.7 defaults: success patterns, zone gate, eval triggers, cooldown relaxation, stall-aware cook timeout, `minKillsAfterAffordable` 0).

### 0.9.10: de-fingerprinting the loop

A timing pass over every 2026-09-02/03 log found server-visible regularities; each has a fix and a knob:

- **No success follow-up.** 0.9.x re-sent the same command 3.5–4.9s after every success to learn the next price (8/8, spread 10%). Now the next tier stays unknown until the balance passes the last paid price × (1 + a growth rolled per success in `retryPriceGrowthMinPct/MaxPct`, 0.2–0.8), logged as `retryAt` on `upgrade_result`.
- **No enable ritual.** Learned prices persist per **username** in `config/ycbotchallenge-state.json` (`state_loaded` / `state_saved`; wiped to the rebirth floor on a rebirth), so a restart never probes. An unknown account gets one `/rebirth` seed per session only after `rebirthSeedMinKillsMin/Max` (5–20) kills **and** `rebirthSeedDelayMin/MaxMs` (2–10 min). After a rebirth the old cost is a floor: one deferred re-probe learns the next goal after `rebirthReprobeMinKillsMin/Max` (15–40) kills and `rebirthReprobeDelayMin/MaxMs` (5–15 min) (`upgrade_plan via=reprobe`), or earlier if money passes the floor × (1 + roll ≤ `rebirthRetryFloorGrowthMaxPct`) (`via=retry-floor`).
- **Rebirth settle.** After our own teleport the bot stands `postRebirthSettleMin/MaxMs` (4–9s; zone advances `postZoneSettleMin/MaxMs` 2–5s), glances around (`postTeleportLookChance`, `mouse_flick reason=settle-look`), and only then retargets (`settle_start` / `settle_end`). 0.9.9 tagged a stale mob one tick after the rebirth teleport.
- **Buy hesitation on long saves.** With `buyHesitationChance` (0.3) an affordable buy is held `buyHesitationMin/MaxMs` (30s–3min) — only when the price has been known for `buyHesitationMinSaveMs` (2 min) and the balance is under `cooldownRelaxBalanceMult` × price. Never in the post-rebirth snowball (back to zone 1, `/swordmax` levels lost, enchants kept, balance 10×/min), never for rebirth, never twice in a row (`upgrade_hesitate`, `upgrade_skip reason=hesitate`). `buyNoticeDelayMaxMs` is 15s.
- **Reaction floor** `reactionDelayMinMs` 200 (was 120). **Bimodal breaks:** `breakShortChance` (0.7) of `breakShortMin/MaxMs` (20–60s), else `breakLongMinutesMin/Max` (5–15 min); `break_start kind=short|long`.
- **Aim and movement.** The re-aim threshold scales with distance (`reacquireFarMult` ×3 at `reacquireFarBlocks` beyond reach, base inside `reacquireFinalBlocks`) — no more 300ms correction chains while walking. Turns over `bigTurnDeg` (60°) land `bigTurnShortMin/MaxPct` (8–15%) short and get a settle flick (`mouse_flick short=true` then `settle=true`); `flickMaxDurationMs` 1100 replaces the 700ms wall. Per-target reach is jittered (`reachJitterPct` 0.2) with an occasional overshoot (`overshootChance`). Long cooks get glances (`cookGlanceAfterMs`, every `cookGlanceMin/MaxMs`; `reason=glance` / `glance-back`). The enchanter's first tab is skipped `enchantSkipFirstTabChance` of the time.

### Enchants during long kills

The server auto-attacks a tagged mob until it dies, so a fresh-stage 50–120s kill is idle time. When the mob's predicted remaining time is at least `enchantMinEtaMs` (45s), the bot right-clicks with the sword to open the **SWORD ENCHANTER**, walks the `enchantTabs` (souls → essence → shards, each spending its own sidebar currency), and for the **first** enchant in slot order that is not `LOCKED`, not maxed, and affordable, opens its `<Name> Upgrade` GUI and clicks **Max Upgrade** (buys level 1 upward for an unowned enchant). Then the next enchant, then the next tab. No optimisation by design.

0.9.19: the enchanter's slots arrive a tick or two after its screen, so an unrecognised container right after the right-click is "not yet", not "wrong", until `enchantOpenTimeoutMs` (the 16:31 log aborted `wrong-gui` 0.2s in and left the menu open); and any menu of ours that nobody is driving is closed after `strayGuiCloseMs` (8s, `stray_gui_close`) instead of idling the bot until the toggle key.

Evidence-based details: the enchanter's title is formatting-only (a font glyph draws the words), so the GUI is recognised by its item tooltips (`enchantSignaturePattern`, "ACTIVATION CHANCE") — and a hand-opened enchanter is therefore never mistaken for a captcha (0.9.8 paused on every manual open). Enchant state comes from the tooltips: `Level: 1,321 / 2,000`, `Price: 7,105,000 Souls`, `LOCKED (Requires Sword Level 50)`; the Max Upgrade hopper's `* Levels: 1` / `* Price: …` decides the final click. The sword's own tooltip (only owned enchants) is logged once per visit as `sword_lore`, never used for decisions.

**When it opens (0.9.11 hazard).** The 0.9.9 "45s mob and 3 minutes" gate only ever opened the menu while a fresh-stage mob was being fought, so visits clustered right after zone advances — a fingerprint. Now every post-kill lull (`via=lull`) and, once per long cook with `enchantCookMinEtaMs` (20s) left (`via=cook`), rolls against a hazard: zero until `enchantHazardRampStartMs` (2 min) since the last visit, rising squared to `enchantHazardFullChance` (8%) at `enchantHazardRampFullMs` (12 min), multiplied by the affordability pull (balance over the cheapest upgradable price seen on the last scan, up to `enchantHazardPullMaxMult` 3×) and by `enchantHazardCookBonus` (2×) mid-cook. With ~5s kills the mean spacing is about 6 minutes with a long tail. No rolls for `enchantPostZoneQuietMin/MaxMs` (30–90s) after a zone advance. Growth since the last visit (`enchantMinBalanceGrowthPct`, 10%) is a soft condition: `enchantCuriosityChance` (10%) of visits happen anyway, scan, and close. `enchant_visit_start` logs `via`, `hazard`, `pull`, `curiosity`.

**What it buys (0.9.12).** No purchase caps: every visit walks all three tabs and Max-Upgrades every affordable enchant on each, at the same human pace per click (`enchantMaxMenuMs` 180s is only a safety cap). The enchanter opens on whatever tab you used last, so the controller first reads which tab is showing from the items' price currency (`enchant_tab_showing`) and only clicks a tab button when it is not already selected — a person does not click the selected tab. Tab buttons are recognised in the top row only, by the tab word or its singular ("SOULS", "Soul Enchants", "ꜱʜᴀʀᴅꜱ"); the raw names of every non-enchant item are logged once per open as `menuItems` for tuning. Affordability always uses the item's own price currency, never the tab's (0.9.11 bought Rocket for 29M essence while checking the souls balance). Only mid-cook visits end when the mob dies; a between-kills visit runs to completion. Every step waits a humanized pause (`enchantLook…`, `enchantTabSettle…`, `enchantBuySettle…`). If the mob is about to die (`enchantWrapUpEtaMs`) the purchase in flight completes and the menu closes; `enchantMaxMenuMs` (40s) and `enchantMaxBuysPerVisit` (6) cap a visit. Events: `enchant_visit_start`, `enchant_menu_open`, `enchant_tab`, `enchant_scan` (the grid with levels/prices), `enchant_pick`, `enchant_upgrade`, `enchant_skip` (cadence / rolled-skip / no-growth / no-sword / none-affordable / max-unaffordable / tab-missing), `enchant_wrap_up`, `enchant_reopen`, `enchant_abort`, `enchant_menu_close`. `enchantsEnabled: false` turns it off; `enchantOpenViaInteract` swaps the synthetic use-key press for a direct interact call if a server build ignores the key.

### Giveaways (0.9.17)

The server announces `NEW GIVEAWAY (30s to enter)` / prize / `Click to Enter!` and counts down; typing `/giveaway` joins (`You have joined the giveaway for Current Lootbox!`). With `giveawaysEnabled` (default on) each announcement rolls `giveawayJoinChance` (0.85), waits a log-normal reading delay (`giveawayJoinDelayMin/MaxMs`, 2.5–12s) and types the command through the same stop-and-type path as every other send; if it cannot go out within `giveawayWindowMs` (25s) it is dropped. Events: `giveaway_seen` (prize, raw packet), `giveaway_plan`, `giveaway_join` (delay, typos), `giveaway_joined`, `giveaway_result` (`us` when our name won), `giveaway_skip` (`disabled`, `chance`, `window`). Joining every giveaway within seconds is its own fingerprint, hence the toggle and the roll. When our own name wins (`<name> has won the giveaway for`, logged `giveaway_result us=true`) the bot says something 1.5–6s later, one of `giveawayWinMessages` (`lfg`, `gg`, `LFG`, `ggs`, `lets gooo`, `W`, ...) picked at random with `giveawayWinReplyChance` (0.9), typed like any line (`giveaway_reply`); `giveawayWinReplyEnabled` turns it off.

### Rebirth upgrades (0.9.17)

`/autorebirth` is unlocked (`serverAutoRebirth`, default on): the server rebirths the moment the cost is covered, so the bot never types `/rebirth` to rebirth (it still probes the GUI to learn the cost for the horizon rule). What each rebirth leaves behind is **rebirth points**, spent in `/rebirth` → the nether star (`REBIRTH UPGRADES`, lore `| Current Points: N`) → the `Upgrades` menu. Drew's order (`rebirthUpgradeOrder`): enchant proc (enchanted book), damage (red dye), essence (magma cream), souls (purple dye), each maxed before the next. A visit runs `rebirthUpgradeDelayMin/MaxMs` (20s–2min) after the post-rebirth settle, or once per session after a rolled kill count for leftover points, always between fights: typed `/rebirth`, a look, read the points (`rebirth_points`; zero = close), click the star, scan the menu (`rebirth_upgrade_menu` logs every tooltip the first time — the item tooltips are **not captured yet**, so the level/cost/maxed patterns `rebirthUpgradeLevel/Cost/MaxedPattern` are best guesses to tune from that log), pick by order (`rebirth_upgrade_pick`), click, settle, re-read: a changed tooltip is a purchase (`rebirth_upgrade_bought`, up to `rebirthUpgradeMaxClicks`), an unchanged one stops the visit (`rebirth_upgrade_stop`). A sub-menu opening from the click is logged (`rebirth_upgrade_submenu`) and closed, never clicked into blind; a revisit follows in 20–90s so the outcome is observed.

### Companions (0.9.28)

Companions multiply money (`Multiplier: 156.38x Money` on the equipped Cow). The bot buys them the way Drew does, on its own: it finds the zone's **Companion Egg** by its hologram (`<Zone> Companion Egg / … / | Price: $… Money` — the zone prefix is never matched, the `Credit Egg` is never touched; `companionEggPattern`, `companionEggExcludePattern`), walks over (`companionEggReach`, `companionWalkTimeoutMs`, `companion_walk`), aims at the pedestal block under the lowest hologram line (`companionEggAimDrop`, pitch swept until the crosshair hits within `companionEggHitRadius`, `companion_aim` with the block id) and right-clicks. In the **Companion Eggs** GUI it clicks `OPEN: [Nx COMPANION EGG]` items (`companionOpenPattern`): the largest that fits the eggs still wanted (`companionEggsMin..Max` rolled per visit), at most `companionMaxIncomeMinutes` of income and `companionMaxBalancePct` of the balance; every open is confirmed by the sidebar money dropping and the delta becomes the per-egg price (the hologram's `$121.3300` format is unverified, so the first open is the probe). Then `/companion`: **Equip Best** (`companionEquipBestPattern`), the four equip slots (`companionEquipSlots`) logged before and after (`companion_equip`), a look at **Fuse Companions** (`companion_gui which=fuse`, nothing clicked yet — fusing is not automated until the layout is seen), and the **sliding-window delete**: keep the newest `companionKeepZones` (2: the current and the previous zone), `/companion bulkdelete ZONE STAGE` for older pairs never held by an equipped companion, at most `companionMaxBulkDeletes` per visit (`companion_delete_plan`, `companion_bulk_delete`). Every GUI is dumped verbatim as `companion_gui` (the fixture net for the next version).

**Finding the egg (0.9.29).** The egg is a real `minecraft:dragon_egg` block on a pedestal, so the bot locates it by scanning the blocks around the player (`companionEggScanRadius` 64 × `companionEggScanVertical` 12, once per 30 s while idle and once per visit; `companion_egg_scan` lists every egg found) and reads the hologram within `companionEggHologramReach` of each to tell the Companion egg from the Credit egg next to it. **Ctrl + Shift + toggle while looking at the egg, bot on or off,** saves it for the current stage (`config/ycbotchallenge-eggs.json`, `companion_egg_spotlight`); with the bot on it also queues the visit. Order of trust per visit: the spotlighted block, the block scan, the saved point for the stage, the hologram alone; when all fail, `companion_plates` dumps the nearest plates so the next fix comes from evidence.

**When.** A sliding window on price vs income, not the top stage (Drew: a batch there costs ~1/4 of the rebirth). The hologram shows the single-egg price in every zone, so the bot logs `companion_price` (stage, price, minutes of income) as it passes. Once `companionStageSettleKills` kills on the stage have made the income figure its own, a visit is due when a batch of `companionEggsMin` eggs costs at most `companionMaxIncomeMinutes` (2.0) of income, the stage is `companionMinStageGain` (2) above the last purchase and the rebirth has fewer than `companionMaxVisitsPerRebirth` (2) visits; fallback when zone buys stop (horizon, zone maxed, or rebirth ETA ≤ `companionRebirthEtaMinMax`) with no visit this rebirth: one visit within `companionEndOfRebirthMaxIncomeMinutes` (8.0). A `companionDelayMin/MaxMs` (10–60 s) pause precedes the walk; `companion_plan` / `companion_skip` carry the numbers. **Ctrl + Shift + toggle** runs a visit now. Aborts log `companion_abort` (phase); three in a row suspend the feature for the session. The walk happens while combat is paused, and combat is reset afterwards so the stop protocol never reads the distance as a teleport.

### Transcend ability (0.9.28)

Q with the sword in hand activates Transcend; the server prints `Your Transcend Ability has been activated (180s Cooldown)` and `… has ended`. The bot reads the cooldown from that line (`transcendCooldownPattern`, fallback `transcendCooldownMs`) and, once it has passed, rolls per kill a chance that ramps from 0 to `transcendFullChance` over `transcendRampMs` — so the press lands somewhere after the cooldown, never on the dot, and never in the first `transcendFirstDelayMin/MaxMs` after enabling. The press is one real drop-key edge with the sword held and no screen open (`transcend_press`); if the hand is empty half a second later the press dropped the sword: `transcend_drop_suspect` and an emergency stop so Drew can pick it up.

### Ignored mobs

Each zone has an `[AFKMOB]` upgrade mob ("[AFKMOB] LVL7 Donkey ❤∞", right-click to upgrade): the same species as the real mobs, standing still, with infinite HP, so every other filter lets it through and the bot used to lock onto it. `ignoreMobPatterns` (default `["[afkmob]", "❤∞"]`, substrings or `/regex/`, case-insensitive) makes such nameplates untargetable; the first sighting of each is logged once as `target_ignored` (with `via`).

**Stay in your zone (0.9.27).** `targetRange` (50) reaches the neighbouring zones and the dominant-pack filter drops out exactly while the local pack is thin — after a respawn broadcast or a zone advance — so the nearest anything won: the 20:35 log has a Chicken picked in zone 7 with a 132° turn 2.7 s after "All mobs have been respawned", and a stray neighbour species in every zone of the session (Villager in lvl9, Horse in lvl7, Mooshroom in lvl8 …). The plate carries the stage (`LVL7 Donkey ❤69B`; the plate regex now parses the untagged shape too, so `tag_intent`/`kill` carry `level` for every mob), and `targetZoneLevelOnly` (default on) makes a mob whose plate level differs from the boss-bar-confirmed zone level never a candidate — mispicks included. The confirmed level is cleared by a teleport or rebirth and set again by the first hit's bar, so the filter is off for those seconds and the dominant filter carries them as before; a respawn broadcast keeps it. Rejections log `target_offzone` once per mob (plate level vs zone level).

**0.9.26: the plate was never the name.** The 19:26 log (and every log before it) shows `target_ignored` firing zero times and no `tag` ever carrying a rarity: on EnchantedMC a mob's plate is not its entity name but a text display riding the mob or floating above it (the AFK Mooshroom carries three lines: `⟡332.12B⟡`, `[AFKMOB] LVL9 Mooshroom ❤∞`, `RIGHT CLICK TO UPGRADE`), so the 0.9.14 rule read a name that was never there and a `target_mispick` roll walked straight into the AFK mob. Three layers now: (1) **holograms** — the mob's passengers, else every plate entity within `nameplateHologramRadiusBlocks` (0.9) horizontally and up to 3.5 blocks above, are its nameplate lines; any line matching `ignoreMobPatterns` makes it untargetable (`target_ignored via=hologram`), and the same lines now feed rarity, level and the log's mob names; (2) **boss bar** (`ignoreByBossBar`) — after the first hit, when every bar mentioning the mob matches (`[AFKMOB] LVL9 Mooshroom`), the target is dropped for the session (`via=bossbar`) instead of being cooked to the timeout; (3) **by hand** — **Ctrl + toggle key** while looking at a mob marks it ignored (`via=manual`, chat notice), persisted by kind and position in `config/ycbotchallenge-ignored.json` and matched within `manualIgnoreRadiusBlocks` (1.5) so it survives rejoins and respawns; Ctrl + toggle on a marked mob removes the mark (`target_unignored`). With nothing in reach the nearest mob within `manualIgnoreAimDeg` (4°) of the crosshair is taken.

### Stop protocol + TTK

- **Stop protocol** (`stopProtocolEnabled`): teleport first, radar second. A single-tick displacement over `teleportThresholdBlocks` (12) stops instantly and *arms* the player radar for the rest of the session (`playerRadarArmAfterTeleport`, default on). Our own `/zone max` advances are exempt — they neither stop the bot nor arm the radar, so zone NPCs and AFK fixtures can never trip it mid-grind. Since 0.9.20 an unexplained teleport first holds still for `teleportExplainGraceMs` (6s): the server's `/autorebirth` teleports with no command of ours to arm it (17:03 log: 28.23Q → 32-block teleport → money 0 at +0.4s → rebirth counter at +4.4s, and the bot had already stopped), so a rebirth signal inside the grace — the `[!] You have successfully rebirthed.` line (`rebirthChatPatterns`), the money collapse, the sidebar counter, or the balance having reached a known rebirth cost — turns it into a rebirth teleport (`teleport_explained`, then the usual post-rebirth settle); no signal = `stop_protocol` as before. One rebirth's three signals reset the economy once (`economy_reset_dedup`). Once armed, a non-whitelisted player continuously within `playerRadarRadius` (48) for `playerRadarDwellMs` (5 s) stops the bot — a lingering stranger is staff. `playerRadarWhitelist` (matches any line of multi-line plates, §-codes and small caps normalized) and `playerRadarIgnoreStationaryMs` remain as second-line defenses; first sightings log as `radar_seen`. Fires a `stop_protocol` event and a red chat notice.
- **TTK** now measures connect → boss-bar-gone (server-authoritative death) instead of client-side entity removal, which ghosts were glitching. A bar that vanishes under `barVanishMinCookMs` with the entity still alive is held for `instantKillConfirmMs` (1.5s, 0.9.21): the entity vanishing or the sidebar money rising after the tag makes it a kill (`kill via=instant`, TTK = the bar's lifetime; `via=death+money` when the bar never rendered at all), nothing makes it a tag that didn't stick. Before this, zone 1 after a rebirth (one-click chickens, bar alive one tick, money a second later) filed 36 of 39 tags as retags, froze the kill counter and the TTK median at the two slow first kills, kept the zone gate closed, and bought 31.5M of swords instead of the first zone.
- **Rarity HP scaling**: kill durations are normalized by `rarityHpScale` (default RARE +15%, EPIC +30%, LEGENDARY +40%) before entering the TTK window, so a tanky legendary doesn't read as slow farming. Mobs with no rarity tag get 1.0 (the nameplate parser can't see a tag that isn't there).

- `zoneMaxTtkMs` (10000) — zone gate base: no `/zone max` while the effective TTK is above this stage's rolled patience or unknown. 0 disables.
- `rebirthSignalWaitMs` (6000) / `rebirthProbeMaxRetries` (1) — after the diamond click, how long to wait for the server's fail line or rebirth signal; how many times per session a probe that never reached the GUI may be re-typed. A probe that reached the GUI and went unanswered is never re-typed.
- `zonePatienceMinMult` / `zonePatienceMaxMult` (0.6 / 1.6) — patience roll band around `zoneMaxTtkMs`, re-rolled per zone change and enable (`zone_patience`). Both 1 = the fixed line.
- `predictedTtkMaxAgeMs` (4000) — a DPS prediction older than this is dropped; the kill median outranks any prediction once three kills of the stage have landed. 0 keeps every prediction.
- `evalFallbackMs` (30000) / `evalOnMoneyIncrease` (true) — upgrade evaluation triggers beyond kills: a timer backstop and any sidebar money increase.
- `cooldownRelaxBalanceMult` (3.0) — the 60s per-kind cap collapses to `commandCooldownMs` while balance ≥ this × the kind's last price. 0 disables.
- `cookStallMs` (15000) — `maxCookMs` only abandons a mob whose boss-bar HP has not dropped for this long.
- `resetTtkOnEnable` (true) — enabling the bot clears the TTK window (`ttk_reset`) so the zone gate re-measures wherever you are: after `/spawn`, a manual zone hop, or an AFK gap. Learned prices are kept.
- `zoneReadyTtkMs`, `zoneMinReadiness` — legacy (pre-0.9.7 readiness curve); inert.
- `scoreboardSnapshotMs` (5000) — how often the canonical multi-currency snapshot is published.
- `sidebarCurrencies` — names parsed from the sidebar (`money`, `souls`, `essence`, `shards`, `credits`).
- `ttkWindowKills` (8) — rolling window for the median TTK. A per-zone baseline is snapshotted a few kills after each zone change and logged via `zone_benchmark` events.
- `upgradeMinIntervalMs` (60s) — backstop ceiling between sends of the same kind. Unaffordable evals do not send.
- `buyNoticeDelayMinMs/MaxMs` (2–8s) — humanized delay between becoming affordable and typing.
- `successSilenceMs` (3000) — no fail line this long after a send = purchase succeeded.
- `retryPriceGrowthMinPct/MaxPct` (0.2–0.8) — unknown-price retry fires when the balance passes old price × (1 + a growth rolled per success). `retryPriceGrowthPct` is legacy.
- `upgradeResponseWindowMs` (4000) — replies are only attributable to our send within this window.
- `expectedTeleportAfterZoneMs` (8000) — stop-protocol exemption after our own `/zone max`.
- `upgradeSpendSettleMs` (2500) — ignore the sidebar this long after a buy (board lags after spending).
- `minKillsAfterAffordable` (0) — extra kills after the balance first covers the target before typing (at a 90s TTK, 1 held 2.75B against a 2.5B stage for a minute and a half).
- `summaryHeaderPattern` / `summaryMoneyPattern` — the `Reward Summary: (60s)` / ` + 17.19B Money` income-rate lines.
- `upgradeFailPatterns` / `upgradeNeedAmountPattern` — anchored fail lines and the gap-amount extractor.
- `upgradeSuccessPatterns` — anchored success lines; the sword pattern's `amount` group is the exact price paid.
- `suffixScales` — manual amount suffixes, e.g. `{"Sx": 1e21}`; they win over learned and built-in scales. Only K M B T Q QQ are built in; the rest is learned.
- `suffixLearningEnabled` (true) / `suffixCrossingMaxJump` (20) — learn new suffixes from sidebar rung crossings (persisted in `config/ycbotchallenge-suffixes.json`); the largest jump between two polls still taken as the next rung.
- `upgradeMaxedPatterns` — anchored response lines meaning a kind is fully upgraded (it is then never sent again).
- `upgradePeriodMinMs/MaxMs`, `zoneEverySwordsMin/Max` — legacy; inert.

### Ninja humanization

`ninja: true` (default) enables the realism layer; `false` restores the old mechanical behavior. All rates are tunable:

- Timing: soft bounds instead of hard clamps (`softClampMarginPct`), rare heavy-tail pauses (`tailChancePerDelay`), per-session bounds jitter (`sessionJitterPct`), fatigue drift (`fatiguePerHour`), and long distractions (`distractionChancePerMinute`, 2–30 s by default).
- Mouse: fast one-shot flicks with a big swoopy curve (~350 ms for a 30° snap at `aimAgility` 1.0 — the old default `0.4` is auto-migrated). Bump size is tunable via `curveBumpMinPct/MaxPct` (7–22% of flick distance by default), sparse idle tremor only, and small flick-tempo regimes (`agilityRegimes`) so no single Fitts regression fits. `mouseChaining` (mid-path re-targets) exists but is off by default — it reads as servo ticking.
- Mistakes: `misclickChance`, `wrongTargetChance`, `sprintHitChance`, `typoChancePerChar` (typo + backspace while typing commands).
- Session theater: `breaksEnabled` with `focusMinutesMin/Max` and `breakMinutesMin/Max`. Focus counts only time the bot is actually running (never wall clock while it is off), and `breaksResetOnToggle` (default on) makes any toggle, stop or captcha pause end the break and start a fresh focus block — the HUD shows `on break — 142s left (toggle to skip)`. Logged as `focus_start` / `break_start`.
- `movingTargetPolicy`: `ignore` (default, ghost filter untouched) or `sometimes` (`movingTargetAttackChance`).

## Captcha auto-solve (local Qwen3-VL)

EnchantedMC's captcha is a **filled map put in your hand** (2026-09-02: it landed in hotbar slot 9 and was selected): the map shows a short random string in colored pixel letters over noise specks, and you type it in chat, **case-sensitive**, within ~30 s. No chat line announces it, so 0.9.13 watches the hands and hotbar (`CaptchaDetector`): a map appearing in a slot that had none fires after `captchaSignalConfirmMs` (`captcha_detected source=held-map|hotbar-map`), and that map id is muted until it is gone. Maps already there at enable time are snapshotted (`hotbar_snapshot`) and never count; `captchaMapAnySlot: false` limits it to the hands. The old triggers stay: a chat line matching `captchaChatPatterns` (never overlay text, and never a player/broadcast line with `»` or a `[rank]` prefix: on 2026-09-03 another player's "next time just captcha him" made the bot screenshot the arena and type a guess into public chat; such matches are now logged `captcha_chat_ignored`) or a server-opened container GUI. Soft hints (`captchaChatHintPatterns`, logged `captcha_hint`) only make a map confirm instantly; they never trigger alone.

With `captchaAutoSolve: true` (default) the bot then:

1. waits `captchaSettleMs`, then reads the map's **own 128×128 pixels** from any hand/hotbar slot (or the nearest item-frame map within `captchaMapSearchRadius`), waiting up to `captchaMapDataWaitMs` for the map-data packet; **no map anywhere = not a captcha the model can read: `captcha_failed stage=capture why=no-map` and a pause for you** (`captchaCaptureMode` `"map"`, the default since 0.9.16; `"auto"` re-enables the HUD-less screenshot fallback downscaled to `captchaScreenMaxPx`, `"screen"` always screenshots). Every capture is dumped to `ycbotchallenge-logs/captcha-<time>-<mode>.png` (`captchaDebugPng`) as the fixture for prompt tuning;
2. POSTs it to `captchaVlmEndpoint` (vLLM in WSL2 serving `Qwen/Qwen3-VL-4B-Instruct-FP8`; Windows `localhost:8000` reaches it once the server listens) with `captchaMapPrompt`, which asks for a **JSON array of single characters** and says the string is not a word; the answer is assembled in code (`ChatClassifier.parseAnswerArray`), case kept (`captchaPreserveCase`);
3. pauses `captchaAnswerDelayMin/MaxMs` (reading it), then **types the answer through the chat screen** like every other send (`ChatTyper`: per-key log-normal delays, `typoChancePerChar` typo + backspace), `captcha_answer typed=true`;
4. resumes when a `captchaSolvedPatterns` line arrives or after `captchaVerifyWaitMs` of silence. On a `captchaRetryPatterns` rejection the second (and last, `captchaMaxAnswers`) guess is the reading with the case of one look-alike letter flipped (`captchaCaseAmbiguous`), built in code with no second model call; a second rejection stops and pauses for you (`captcha_pause reason=answers-exhausted`). Never spam.

**0.9.26: a running ballot, a map that stays is a no, and the typo that was not a glitch.** The 19:43 log: the bot read `Kra` from its x4 render, typed it, heard nothing for 12 s, declared the captcha solved and resumed; the answer was `KrA` (Drew, by hand). Bench on the exact image the bot sent: x4 smoothed reads `Kra` 12 of 12 times at any temperature, x3 and x2 read `KrA` 8 of 8, and a "which case is it" prompt still says `Kra` — the model is consistently wrong on that one rendering, and the cross-check that had it right was waiting for a rejection line the server never sends (`latest.log` 13:43: silence after a wrong answer; silence after a right one too, the map just leaves the hand). Three changes. (1) **Ballot**: the map is rendered once at every scale in `captchaVoteRenders` (`x4bil, x3bil, x2near, x5bil, x3near`) and one background reader reads them in turn, the schedule at temperature 0 then at `captchaVoteTemperature` (0.6), up to `captchaVoteMaxReads` (12); every reading is a vote, the first answer is the leader once the human reading pause has passed and `captchaVoteMinReads` (3) votes are in, voting continues while the answer is verified, and a rejection sends the best-supported alternative (`captcha_vote` at each send and rejection with the tallies; `captcha_candidates via=ballot`). On the certified captures the vote is right on all of KrA, p8b and pnGe where the primary render alone was wrong on KrA; `python tools/captcha_bench.py --vote` replays it. (2) **Map still held = rejected** (`captchaMapHeldRejectMs`, 7 s): the answered map still in a hand or the hotbar that long after the answer logs `captcha_map_persists` and the next candidate goes out — the `captchaMaxAnswers` (2) cap still holds; and any re-detection of the map already answered from continues with the remaining candidates instead of re-reading it. (3) **Typing**: a typo used to advance past the intended character, so the field genuinely read `/zne max` while the original string was sent — what was on screen was not what was sent. The keystroke rule is now a pure, tested step (`ChatTyper.step`): the slip goes in, the backspace takes it out, the intended character follows; the field ends exactly as the command, and that is what is sent (`typedMismatch:true` in `upgrade_send` / `captcha_answer` if it ever differs). The `KrA` capture is certified as `tools/captcha-fixtures/KrA-map128.png`.

**Certified fixtures and the bench (0.9.22).** Every captcha whose answer is known lives in `tools/captcha-fixtures/` (`fixtures.json`: file, answer, provenance) — today `pnGe` (2026-09-02 screenshot, board crop on the 128 px map grid) and `p8b` (2026-09-03 17:38, the bot's own map capture; it read `pBb` at the 256 px render and Drew confirmed `p8b`). `python tools/captcha_bench.py` runs prompts × render scales × sampling against them with the mod's own answer parsing and prints greedy and sampled hit rates plus the best two-render pairs; run it before touching `captchaMapPrompt`, `captchaMapScale` or `captchaMapSmooth`, and add each new capture with its accepted answer. The 12-sample run that set 0.9.22: shipped prompt at ×4 smoothed 2/2 greedy, 23/24 sampled; ×2 nearest 1/2 (p8b → pBb every time); ×4 nearest 0/2; a digits-coaching prompt over-corrects (`8bb`). Hence `captchaMapScale` 4 (migrated from 2), a `captchaSecondScale` (3) cross-check whose disagreement is the second guess, and `captchaLookalikes` (`B8,O0,S5,Z2,…`) for the second guess when both agree. The server's `Please enter the captcha on the map.` is its re-prompt after a wrong answer (it arrived 5 s after `pBb`), so it is a `captchaRetryPatterns` signal, `captchaVerifyWaitMs` is 12 s so it lands inside the window, and a chat re-prompt for a map already answered continues with the next guess (`captcha_reprompted`) instead of re-reading it. The reading pause is 2.5–5 s (`captchaAnswerDelayMin/MaxMs`).

**Image size matters more than the prompt.** Bench 2026-09-03 on the `pnGe` capture with the local 4B model (0.1–0.4 s per call): the JSON-array prompt read it right on every input from 192 px to 1024 px wide (6/6 samples at temperature 0.7), while the native 1605 px screenshot and a 128 px map upscaled ×4 with nearest neighbour misread (`pinge`, `prGe`) and ×6 was garbage; ×2 nearest or ×4 bilinear read right. Hence `captchaMapScale` 2 (migrated from 4) with `captchaMapSmooth` for anything larger, and the screenshot cap. Word-shaped prompts (`ANSWER: <word>`) returned `pinc`/`pInGe`, and a per-letter colour enumeration inserted a phantom `i` every time: ask for characters, not words.

**VLM health.** On enable and every `captchaVlmHealthIntervalMs` the bot GETs `captchaVlmHealthUrl` (`vlm_health online models latencyMs`); while it is down the HUD shows `captcha VLM: offline` in red and a captcha pauses at once (`captcha_pause reason=vlm-offline`) instead of retrying against a dead port. If the server serves exactly one model under another id it is used (`captchaVlmModelAuto`, `vlm_model_auto`). Start vLLM before the bot; check with:

```bash
curl http://127.0.0.1:8000/v1/models
```

Drew's serve line (WSL2, 3080 Ti): `vllm serve Qwen/Qwen3-VL-4B-Instruct-FP8 --host 0.0.0.0 --port 8000 --max-model-len 4096 --gpu-memory-utilization 0.75 --max-num-seqs 2 --limit-mm-per-prompt '{"image": 1, "video": 0}'`. A cloud OpenAI-compatible endpoint needs only `captchaVlmEndpoint`/`captchaVlmModel`; the key is read from the `YCBOT_VLM_KEY` environment variable (never the config file).

Events: `captcha_detected`, `hotbar_snapshot`, `captcha_captured` (mode, where, px, png), `captcha_candidates` (raw reply), `captcha_answer` (typed, typos), `captcha_solved` / `captcha_failed` / `captcha_pause` (reason), `captcha_hint`, `chat_raw` (unclassified server lines, ≤ `chatRawPerMinute`), `vlm_health`, `vlm_model_auto`. Set `captchaAutoSolve: false` for the old hard pause.

The Sonar defaults (chat-triggered captcha, 3–4 lowercase letters, `ANSWER`/`ALT` lines with `captchaPrompt` and `captchaRetryPrompt`) are kept for chat/GUI-triggered captchas with no map in reach.

## How it detects progression

Rebirths: sidebar counter going up = rebirth; counter dropping = reset = ascension (plus chat-message patterns as a second signal, same for prestige). Boosts: boss bar titles, tracked as start/end and stamped into every event's context. Balances: the sidebar rows (`balance` on change, `scoreboard_snapshot` every 5s); the reward summary feeds only the income rate. Zone: own teleport, boss-bar mob level, respawn broadcast or a sidebar Zone row. Log events: `scoreboard_snapshot`, `balance`, `income`, `income_summary`, `upgrade_plan` / `upgrade_skip` (with `via` = kill/money/timer, `ttkMs`, `zoneGate`, `swordFloor`/`zoneFloor`), `upgrade_send`, `upgrade_chat`, `upgrade_result` (`paid`, `extraLevel` for multi-level `/swordmax`), `upgrade_maxed`, `upgrade_response_raw`, `zone_benchmark`, `zone_teleport`, `zone_change`, `boss_level`, `ttk_reset`, `economy_reset`, `target_abandoned` (`sinceHpDropMs`), `focus_start`, `enchant_*` (see Enchants during long kills) (plus ninja noise: `misclick`, `target_mispick`, `sprint_hit_slip`, `distracted`, `break_start`, `aim_regime`).
